# 학생 신뢰성 워크플로

버전 0.7.0 · 2026-09-04

## 1. 제품 판단

코스모스 LXP 앱 후기에는 로그인, 주차별 메뉴, 파일 다운로드, 알림, 로딩과 뒤로가기 문제가 반복적으로 나타난다. 전북대 LMS 3.0에는 이미 AI 튜터·요약·과제 지원이 있으므로 이 MCP는 범용 챗봇을 복제하지 않고 **놓침 방지, 상태 재확인, 변경 추적, 자료 무결성**에 집중한다.

근거: [전북대 LMS 3.0 안내](https://portal.jbnu.ac.kr/web/Board/209099/detailView.do) · [코스모스 LXP App Store](https://apps.apple.com/kr/app/%EC%BD%94%EC%8A%A4%EB%AA%A8%EC%8A%A4-lxp/id6757424159) · [코스모스 Google Play](https://play.google.com/store/apps/details?id=kr.coursemos.android2&hl=ko)

## 2. 전체 흐름

```text
LMS 읽기
  ├─ 구조화 데이터: 과제·퀴즈·마감
  ├─ 화면 데이터: 공지·제출 상태·자료
  └─ 변경 기록: 로컬 스냅샷 + Moodle updates_since
          │
          ▼
정규화·판단(로컬)
  ├─ AttentionItem: 지금 학생이 확인할 일
  ├─ SubmissionCheck: 상세 화면 기반 제출 판정
  └─ CalendarCandidate: 외부 쓰기 전 확정 일정 후보
          │
          ▼
사용자 경험
  ├─ 학생 확인함: 상위 행동 3개
  ├─ 제출 안심 확인: 판정·근거·주의
  └─ 호스트 조정: 캘린더 검색 → 중복 판정 → 승인된 쓰기
```

LMS 읽기, 로컬 판단, 외부 캘린더 변경을 서로 다른 계층에 둔다. 따라서 캘린더 연결이 없거나 Claude·Codex 등 호스트가 바뀌어도 LMS 조회와 우선순위 판단은 그대로 동작한다.

## 3. 상태와 불변 조건

### 학생 확인함

- `action_required`: 확정 마감처럼 학생 행동이 필요한 항목
- `review_required`: 수정 공지, 사라진 과제, 모호한 상태처럼 사람 판단이 필요한 항목
- `information`: 새 자료처럼 확인 우선순위가 낮은 항목

우선순위는 `critical → high → normal → low`, 같은 우선순위에서는 가까운 마감이 먼저다. 첫 화면은 최대 3개다. 처음 실행은 변경을 새 항목으로 오인하지 않고 기준 스냅샷을 만든다.

### 제출 확인

- 목록 캐시가 아니라 과제 상세 화면을 다시 읽는다.
- `draft`는 파일이 있더라도 최종 제출로 간주하지 않는다.
- `submitted`는 LMS의 현재 표시를 확인했다는 뜻이며 학교가 발급한 공식 영수증은 아니다.
- 확인 지문은 상태 비교용이고 인증 정보·공지 본문·과제 설명을 포함하지 않는다.

### 캘린더 후보

- 구조화된 `dueAt`이 있는 LMS 항목만 `confidence=exact` 후보가 된다.
- 상대 날짜·공지 본문 추론은 자동 반영 후보가 아니다.
- 같은 LMS 항목은 안정적인 SHA-256 fingerprint를 갖는다.
- 후보 생성은 캘린더에 아무것도 쓰지 않는다.
- 외부 쓰기는 호스트가 기존 캘린더를 검색한 뒤 현재 요청 또는 저장된 상시 동의 범위에서만 수행한다.

### 자료 다운로드

- LMS 첨부 경로와 지정 다운로드 루트만 허용한다.
- 200MB 한도, 임시 파일 쓰기, 원자적 확정을 유지한다.
- 기존 파일과 새 데이터의 SHA-256이 같으면 기존 파일을 반환한다.
- 이름이 같지만 내용이 다르면 번호가 붙은 새 버전으로 보존한다.

## 4. 0.6.0 구현 범위

| 단계 | 도구 | 구현 결과 |
|---|---|---|
| 종합 수집·판단 | `get_attention_inbox` | 마감과 변경을 합치고 상위 3개 행동 제시 |
| 제출 재확인 | `check_assignment_submission` | 최종 제출·초안·미제출 판정과 확인 지문 |
| 캘린더 준비 | `get_calendar_sync_candidates` | 확정 후보·fingerprint, 외부 쓰기 없음 |
| 자료 신뢰성 | `download_course_material` | SHA-256과 동일 파일 재사용 |

## 5. 다음 구현 순서

1. 공지 상세에서 날짜·장소·행동을 추출하되 `명시 문장`과 `추론`을 분리하고 fixture 계약 테스트를 추가한다.
2. 캘린더 제공자 검색 결과를 입력받아 `create/update/no-op/review`를 계산하는 `preview_calendar_sync`를 구현한다.
3. 과목·대상 캘린더·자동 반영 수준을 저장하는 로컬 정책 저장소를 구현한다. 토큰은 저장하지 않는다.
4. 15~30분 예약 실행은 호스트 자동화로 구성하고, 변화 없음은 알리지 않는다.
5. 학습진도/온라인출석부의 실제 학생 화면 구조를 비식별 fixture로 확보한 뒤 진도 기록 이상 감지를 추가한다.
6. 성적·피드백은 별도 옵트인과 민감정보 최소화 정책을 먼저 작성한 뒤 구현한다.

각 단계의 출시 조건은 반복 실행의 멱등성, 부분 실패 표시, LMS 화면 구조 변경 시 안전한 실패, 비밀값·본문 비저장, 외부 변경의 명시적 권한 경계다.
