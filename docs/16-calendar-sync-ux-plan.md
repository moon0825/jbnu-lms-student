# LMS 일정 동기화 UX·안전 설계

## 1. 목표와 경계

학생이 공지·과제·퀴즈·수업 변경을 매번 직접 옮기지 않아도, **한 번 정한 정책 안에서** 연결된 캘린더에 반영되도록 한다. 편의성을 위해 인증 정보나 LMS 원문 전체를 외부 캘린더로 보내지는 않는다.

- JBNU LMS MCP는 계속 읽기 전용이며 캘린더 제공자의 비밀번호·토큰을 저장하지 않는다.
- LMS MCP는 표준화된 `CalendarCandidate`와 동기화 계획만 만든다.
- Codex, Claude 등의 호스트가 사용자가 연결한 Google Calendar·기타 캘린더 도구로 조회·생성·수정한다.
- 최초 1회에는 대상 캘린더, 과목 범위, 자동 반영 수준을 사용자가 승인해야 한다.
- 이후에는 승인된 범위의 확정 일정만 자동 반영한다. 애매한 해석, 충돌, 삭제는 사용자에게 제안한다.

이 분리는 Google 전용 의존성과 자격 증명 보관을 피하고, 같은 LMS MCP를 여러 AI 플랫폼과 캘린더 제공자에서 재사용하기 위한 것이다.

## 2. 권장 기본 설정

첫 설정 화면은 다음 세 가지만 묻는다.

1. 저장할 캘린더: 별도의 비공개 `LMS` 캘린더 권장
2. 자동 반영 범위: 전체 과목 또는 선택 과목
3. 자동화 수준: `도움형 자동` 권장

`도움형 자동`의 기본 정책은 다음과 같다.

| 후보 | 처리 |
|---|---|
| LMS가 구조화된 마감 시각을 제공하는 과제·퀴즈 | 중복 확인 후 자동 생성·변경 |
| 공지에 날짜·시각·행동이 명확하게 적힌 시험·발표·보강 | 미리보기 또는 사용자가 과목별로 허용한 경우 자동 생성 |
| `다음 주`, `수업 전`, `순차 발표`처럼 해석이 필요한 표현 | 검토함에 제안, 자동 생성 금지 |
| 기존 수동 일정과 비슷하지만 동일성이 불확실함 | 병합 제안, 자동 삭제·덮어쓰기 금지 |
| LMS에서 사라지거나 취소된 일정 | `취소 가능성` 표시 후 확인 요청, 자동 삭제 금지 |

사용자는 언제든 과목별 자동 반영을 끄고, 전체 동기화를 일시 정지하거나 로컬 연결 기록을 지울 수 있어야 한다.

## 3. 사용자 경험 흐름

### 3.1 최초 연결

1. LMS 연결 상태를 확인하고 공식 SSO 브라우저에서 사용자가 직접 로그인한다.
2. 연결된 캘린더 목록을 보여 주되 캘린더 계정 비밀번호나 인증 코드를 요구하지 않는다.
3. 새 `LMS` 캘린더 생성 또는 기존 캘린더 선택을 안내한다.
4. 최근 일정 후보를 실제로 쓰지 않고 미리보기한다.
5. `확정 일정 자동 반영`, `공지 해석 일정은 검토`, `변경 때만 알림` 정책을 한 화면에서 승인받는다.

### 3.2 평상시 동기화

1. 예약 실행이 `get_recent_changes`와 마감·공지 조회를 수행한다.
2. 새 항목을 일정 후보로 정규화하고 신뢰도를 매긴다.
3. 대상 기간의 캘린더 일정을 먼저 검색해 중복과 변경을 판단한다.
4. 승인 정책에 포함된 확정 일정만 생성·수정한다.
5. 변화가 없으면 알리지 않는다. 생성·변경 요약, 충돌, 실패, 사용자 판단이 필요할 때만 알린다.

권장 주기는 15~30분이며, 알림은 건별 폭탄 대신 하루 요약과 긴급 변경을 결합한다.

### 3.3 사용자가 대화로 요청할 때

- “이번 달 할 일 넣어줘”: 후보와 중복 결과를 먼저 요약하고 승인 범위를 확인한 뒤 반영한다.
- “앞으로 알아서 해줘”: 대상 캘린더와 과목별 정책을 1회 확정하고 예약 실행을 만든다.
- “이 공지만 일정으로”: 해당 원문을 확인하고 단일 일정 미리보기를 제공한다.
- “틀린 일정 고쳐줘”: LMS 원문과 현재 캘린더의 차이를 보여 주고, 관리 중인 일정만 수정한다.

## 4. 일정 후보 모델

```text
CalendarCandidate
- sourceKind: assignment | quiz | announcement | course_event | material
- sourceKey: courseId + moduleId 또는 boardId + articleId
- sourceUrl: 허용된 LMS 원문 경로
- courseLabel: 선택적 표시명
- title: 짧은 일정 제목
- startAt / endAt / allDay / timezone
- action: submit | attend | study | check
- confidence: exact | explicit_text | inferred
- evidence: 날짜를 판단한 짧은 근거와 필드명
- revision: 원문 변경 판별값
```

캘린더에는 필요한 최소 정보만 쓴다. 기본 제목은 `[LMS] 과목 - 할 일`, 공개 범위는 비공개이며, 설명에는 짧은 요구사항·원문 링크·마지막 확인 시각만 포함한다. 공지 전문, 학번, 이메일, 교수자 연락처, 로그인 정보는 포함하지 않는다. 사용자가 원하면 과목명도 일반화할 수 있다.

## 5. 중복·변경 처리

로컬 SQLite에 본문이 아닌 연결 정보만 저장한다.

```text
lms_event_key -> provider + calendar_id + event_id + source_revision + last_sync
```

처리 순서는 다음과 같다.

1. `sourceKind + sourceKey + action`의 안정적인 키로 관리 중인 일정을 찾는다.
2. 없으면 대상 기간의 캘린더를 검색한다.
3. 제목 정규화, 시작·종료 시각, 과목, 원문 URL을 비교한다.
4. 완전 일치면 아무 작업도 하지 않는다.
5. 관리 중인 일정의 LMS 값이 바뀌면 제목·시각·설명을 갱신하고 변경 전후를 알린다.
6. 사용자가 만든 것으로 보이는 유사 일정은 `병합`, `둘 다 유지`, `앞으로 무시`를 제안한다.
7. 사용자가 캘린더에서 직접 고친 필드는 기본적으로 보존하고, LMS와 충돌하면 선택을 묻는다.

삭제는 가장 보수적으로 다룬다. LMS 항목이 사라져도 곧바로 캘린더에서 지우지 않고 `원문에서 확인되지 않음` 상태로 두어 취소·과목 비공개·일시 오류를 구분한다.

## 6. 주요 사용 사례와 예외

| 상황 | 기대 동작 |
|---|---|
| 과제 마감이 새로 게시됨 | 확정 시각이면 정책에 따라 생성, 원문 링크 포함 |
| 마감이 연장됨 | 관리 중인 일정 갱신, `기존 → 변경` 한 줄 알림 |
| 퀴즈에 시작·종료 시간이 있음 | 시작과 종료를 구분해 한 일정 또는 정책에 따른 두 알림으로 표현 |
| 시험·발표 일정이 공지 본문에만 있음 | 명시 날짜면 후보, 상대 날짜면 검토함 |
| 휴강·보강·강의실 변경 | 기존 수업 일정과 충돌 여부를 보여 주고 변경 제안 |
| 제출 마감과 권장 완료일이 다름 | 마감은 확정 일정, 권장 완료일은 개인 계획으로 구분 |
| 조별·분반별 일정 | 사용자 소속이 확인되지 않으면 자동 생성하지 않고 대상 확인 |
| 반복 수업·매주 자료 공개 | 반복 일정은 최초 승인 후 생성, 예외 주차를 별도 반영 |
| 이미 사용자가 같은 일정을 만듦 | 유사 중복으로 묶어 병합 제안 |
| LMS 항목이 삭제되거나 접근 불가 | 자동 삭제하지 않고 재확인·보류 |
| 자정 마감·종일 일정·서머타임 | 원본의 Asia/Seoul 시각과 종일 여부를 명시해 저장 |
| 여러 캘린더가 연결됨 | 과목별 목적지를 기억하고 모호하면 기본 `LMS` 캘린더 사용 |
| 캘린더 연결 만료·네트워크 오류 | 로컬 후보를 보류하고 다음 실행에서 재시도, 중복 생성 방지 |
| 사용자가 자동화 일정을 직접 수정함 | 사용자 수정 보존, 충돌 해결 전 자동 덮어쓰기 금지 |
| 과목을 숨기거나 수강 철회함 | 해당 과목 자동 반영 중지 제안, 기존 일정 일괄 삭제 금지 |

## 7. 도구와 스킬 확장안

LMS MCP에 다음 읽기·계획 도구를 단계적으로 추가한다.

- `get_calendar_sync_candidates`: 기간·과목별 구조화된 확정 후보와 안정적인 fingerprint 반환 — **0.6.0 구현**
- `preview_calendar_sync`: 생성·수정·중복·검토 항목을 작업 없이 계산
- `set_calendar_sync_policy`: 로컬 정책 저장. 캘린더 토큰은 저장하지 않음
- `get_calendar_sync_status`: 마지막 확인·보류·실패·정지 상태 표시
- `resolve_calendar_conflict`: 사용자가 선택한 병합 정책을 로컬 계획에 반영
- `ignore_calendar_candidate`: 특정 항목 또는 패턴을 다시 제안하지 않도록 기록

스킬은 연결된 캘린더의 검색 도구를 먼저 사용하고, 쓰기는 현재 대화의 명시적 요청 또는 사전에 저장된 자동화 정책 범위에서만 수행한다. 표준 MCP 서버가 다른 MCP 서버를 직접 호출한다고 가정하지 않으며, 호스트의 스킬·예약 작업이 둘을 조정한다.

## 8. 단계별 출시 계획

### 1단계 — 안전한 미리보기

- 일정 후보 정규화와 신뢰도 규칙 — **구조화된 마감 범위 구현**
- 캘린더 쓰기 없는 미리보기
- 검색 기반 중복·변경 제안
- 파서 계약 테스트와 개인정보 최소화 테스트

### 2단계 — 승인된 자동 생성·수정

- 전용 캘린더와 과목별 상시 동의
- 확정 일정의 멱등 생성·변경
- 로컬 연결 DB, 일시 정지, 감사 로그, 복구 가능한 변경 이력
- 의미 있는 변화에만 알리는 예약 작업

### 3단계 — 여러 플랫폼·제공자

- Google Calendar 외 제공자 어댑터 계약
- Codex와 Claude에서 동일한 후보·정책 포맷 사용
- 충돌 검토함, 과목별 고급 규칙, 내보내기·연결 기록 삭제

출시 기준은 같은 LMS 항목을 반복 실행해도 일정이 하나만 존재하고, 날짜 변경은 기존 일정을 갱신하며, 애매한 공지·수동 일정·삭제 후보를 자동으로 덮어쓰지 않는 것이다.
